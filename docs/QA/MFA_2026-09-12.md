# Recoverable MFA — 2026-09-12

Follow-up: the [M3 operations record](M3_OPERATIONS_2026-09-12.md) supersedes the
remaining-work list below for proxy limits, API schemas, notifications and key

## Scope and outcome

M3 now includes real authenticator enrollment and replacement at
`/dashboard/security`, ten one-use recovery codes, and a separate operator
command for granting platform-administrator access. Enrollment is available
to verified active users and never changes their role. This is local
implementation evidence, not a deployment or a declaration that M3 is complete.

The existing Next.js / NestJS / PostgreSQL stack is retained. A migration adds
encrypted pending setup, its session binding and expiry, the last accepted
TOTP counter, recovery-code hashes and MFA audit event types.

## Security behavior

- Setup requires the current password and an active verified session. Replacing
  an existing authenticator also requires a fresh authenticator or recovery code.
  Pending setup expires after ten minutes and leaves the current factor active.
- Confirmation requires the password and a code from the new authenticator in
  the same session that began setup. It revokes previous sessions and issues a
  new AAL2 session through the existing HttpOnly cookie proxy.
- Authenticator secrets use AES-256-GCM with user-bound authenticated data and
  an external 32-byte key. Recovery codes contain 128 random bits each and are
  stored only as SHA-256 hashes. Responses containing secrets use `no-store`.
- User-row locks make factor consumption and session creation atomic. A TOTP
  counter or recovery code cannot be reused, including concurrent requests.
  Recovery login revokes other sessions and leaves MFA enabled.
- Password reset cancels pending setup and revokes sessions; it does not remove
  the enabled factor or recovery-code requirement.
- The UI shows recovery codes once, requires acknowledgement before dismissing
  them, and warns on browser unload while they remain visible. Codes are not
  stored in localStorage. Internal navigation can still dismiss this view, so
  save codes before leaving. Replacing the authenticator creates a new set.
- Admin promotion requires a verified active account with encrypted confirmed
  MFA and unused recovery codes. It revokes sessions and records an operator
  audit event. There is no public or tenant promotion endpoint.

The implementation decision is in [Auth/RBAC](../DECISIONS/AUTH_RBAC.md).
Factor replacement, independent recovery and reauthentication were checked
against the [OWASP MFA guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html).

## Local operator runbook

1. Configure `DATABASE_URL`, email delivery and the existing API/web settings
   from their `.env.example` files. Generate a dedicated `MFA_ENCRYPTION_KEY`
   using `openssl rand -base64 32`, and store it in the API's secret environment.
   Keep it stable across restarts and shared by all API instances. The fixed
   key in test configuration is exclusively for disposable test accounts.
2. Apply the migration with
   `npm run prisma:migrate:deploy --workspace @daify/api`.
3. Sign up normally, verify email and open `/dashboard/security`. Enter the
   current password and add the displayed secret manually to an authenticator
   app: DAIFY, time-based, six digits, 30 seconds, SHA-1. Confirm with its code
   and save all ten recovery codes securely. QR enrollment is not implemented.
4. Only if platform access is explicitly intended, an authorized operator with
   the target database and encryption key configured runs:

   ```bash
   npm run admin:promote --workspace @daify/api -- user@example.com
   ```

   This command changes a real role and revokes the user's sessions. Confirm the
   target environment and account first. The CLI validates secret decryption
   before promotion; the role gate is also enforced in its transaction.
5. Sign in again with the password and exactly one authenticator or unused
   recovery code. A code just used for enrollment/login cannot immediately be
   reused; wait for the authenticator's next code.

No real account was promoted, no real email was sent, and no provider or
deployment was configured during this change. Tests used an isolated local
PostgreSQL 17 database.

## Validation

All 89 unique automated tests passed. Build, TypeScript, lint, Prisma formatting
and migration status checks also passed; all three migrations were applied.

- API: 52 tests across nine suites, including encryption/tampering, session-bound
  setup, expiry, replacement, concurrent TOTP and recovery consumption,
  password-reset preservation and administrator promotion requirements.
- Web: 20 browser cases, with the existing real-account/workspace/team journey
  extended through MFA enrollment, session rotation and recovery login.
- Preserved prototype: 17 browser cases.
- Development and compiled-production web runs are recorded separately; they
  are the same 20 cases, not 40 unique tests.

The first production run exposed a refresh/reload collision after dismissing
recovery codes. The Done action already updates local state, so its redundant
server refresh was removed. The rebuilt production suite passed all 20 cases,
including the immediate reload and recovery login. Final desktop/mobile
screenshots were inspected from that production run.

Logs and desktop/mobile screenshots are in
[the evidence directory](evidence/2026-09-12-mfa/). Screenshots show the completed
settings screen, not authenticator secrets or recovery codes. Playwright failure
traces can contain disposable test credentials and are not included as evidence.

## Remaining work

- M3: proxy-aware per-client throttling across the Next/API boundary, complete
  request/response schemas for the remaining endpoints, external SMTP delivery
  and retry validation, and final acceptance review.
- Before real admin rollout: secure key backup and restore verification, a
  reviewed key-rotation procedure and account-owner notifications for MFA
  changes/recovery. Replacing the key without re-encrypting secrets breaks
  authenticator access. Key rotation is not automated.
- Legacy test-era plaintext MFA secrets can upgrade after successful TOTP login;
  newly enrolled secrets are encrypted, and operator promotion rejects plaintext.
- Losing both the authenticator and all recovery codes has no self-service
  bypass. A separately reviewed identity-verification/support recovery process
  remains future work. Password-reset email alone cannot remove MFA.
- M1's outstanding broad visual/accessibility and observed CI gates remain.
  M4 menu CRUD and subsequent publishing/QR milestones have not started.
