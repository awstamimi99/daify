## Implemented behavior

- Organization/location-scoped menu listing, creation, updates and soft archive;
  location updates/archive with currency changes rejected while active menus exist.
- Sections and items with ordering, moves, visibility, availability, featured flags,
  structured allergens/dietary tags and currency-specific decimal precision.
- Explicit translation tables for menus, sections, items and image descriptions;
  canonical language tags, required default-language names and completeness v1.
  Secondary names may remain incomplete in a draft. Descriptions/image alt text
  are optional and reported separately. English-only, Arabic-only, bilingual and
  additional menu languages are supported.
- Database transactions lock organization then menu, recheck membership and reject
  stale draft revisions with 409. The editor preserves unsaved values on failure
  and offers explicit reload. Saving one form warns before discarding other edits.
- Staff can update availability only; viewers read; scoped managers and outsiders
  cannot access another branch/tenant. Every draft mutation records a security event.
- Private validated JPEG/PNG/WebP upload, metadata removal, orientation correction,
  immutable object keys, authenticated reads, localized image descriptions and
  detachment. No storage keys are exposed through draft JSON.
- `/dashboard/menus` and `/dashboard/restaurant` persist through the API. Shared
  form fields now use unique React IDs, preventing repeated editor fields from
  stealing each other's labels. Arabic content uses RTL fields/headings.

## Running locally

Use the root README's database/API/web setup. Apply migrations with
`npm run prisma:migrate:deploy --workspace @daify/api`. Set the API's
`MEDIA_STORAGE=local`; `MEDIA_LOCAL_DIR=.data/media` resolves relative to the API
working directory. The ignored directory contains private processed files, while
PostgreSQL owns associations and translations. Do not clear it for a real workspace.

For verification, both `DATABASE_URL` and `TEST_DATABASE_URL` must name a migrated,
disposable PostgreSQL database containing `test` in its name. Run `npm run test:api`,
then `npm run build` and `WEB_TEST_PRODUCTION=true npm run test:web`; do not run API
fixture cleanup concurrently with browser journeys. `npm run test:prototype`
checks the preserved HTML/JS product separately. Set `QA_EVIDENCE_DIR` to an existing
absolute directory to capture the dashboard/editor screenshots.

## Production media setup still required

1. Select an S3-compatible service and private bucket. Configure `MEDIA_STORAGE=s3`,
   `S3_ENDPOINT` (HTTPS), `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID` and
   `S3_SECRET_ACCESS_KEY` through the runtime secret store. Use bucket-scoped
   read/write/delete credentials and disable public access. Values are documented
   in `apps/api/.env.example`; none are configured by this change.
2. Deploy to a test environment and run the upload/read/detach journey against the
   actual provider. Verify unauthenticated and wrong-tenant reads fail and restart
   the API to confirm media persistence. The S3 adapter is implemented and builds;
   no live S3/R2 integration has been verified.
3. Verify private-bucket policy, network/TLS/timeouts, storage failure recovery,
   credential rotation, backups and database/media restoration together.

Uploads are at most 2 MiB and 12 megapixels, with at most five active images per
item. Processing re-encodes to JPEG, at most 1600×1600, stripping metadata; this
also removes alpha transparency. JSON body limits are 3 MiB on image uploads and
100 KiB elsewhere in both API and proxy. Animations are rejected. Failed attachment
attempts remove their just-written objects when possible; failed cleanup is logged.
Detached/archived objects are retained. Scheduled orphan cleanup, responsive image
variants, direct signed uploads and public CDN delivery are deferred pipeline work.

The dependency audit reports **0 critical / 7 high** production dependency findings,
