# M6 sandbox payment webhooks - local verification

Continuation on `feat/m6-billing`, starting from checkpoint `709125a` and its
unfinished webhook implementation. M6 remains in progress. This report supplements
[the original sandbox checkpoint](M6_2026-09-14.md).

## Implemented and verified

- `POST /api/v1/billing/myfatoorah/webhook` accepts sandbox Webhook V2 payment
  notifications using the dedicated account webhook secret. Invalid signatures
  are rejected; missing sandbox configuration disables receipt and processing.
- HMAC-SHA256 verification follows the provider's ordered payment fields, with
  constant-time comparison. Only the signed invoice ID binds a notification to
  a server-created checkout. Unknown invoices have no effect.
- The durable inbox stores the checkout ID and a digest of signed fields, plus
  processing timestamps and attempt count. It does not persist customer/card
  payloads. Changing unsigned references, amounts or UDF does not bypass replay
  detection or change subscription decisions.
- The background reconciler drains bounded inbox batches and queries authoritative
  payment status before granting access. Duplicate and reordered events cannot
  extend a paid subscription twice or reverse an already completed payment.
- Workers claim a two-minute lease. Failed attempts retry with exponential delay,
  capped at one hour. Duplicate deliveries preserve backoff and completion state.
  Attempt-conditional updates prevent an expired worker from completing or
  rescheduling a newer worker's claim. Abandoned leases can be reclaimed.
- Periodic checkout reconciliation remains responsible for missed notifications,
  notifications arriving before an invoice ID was saved, and payment status that
  is still pending when an inbox entry is processed.
- OpenAPI documents the endpoint, request shape and disabled/error responses.
  Production configuration rejects the sandbox webhook secret.

Protocol references, checked on 2026-09-21:
[payment event model](https://docs.myfatoorah.com/docs/webhook-v2-payment-status-data-model)
and [signature algorithm](https://docs.myfatoorah.com/docs/webhook-signature).

## Account setup and remaining acceptance

For a project-owned sandbox account, configure `BILLING_MODE=sandbox`, its test API
key, and `MYFATOORAH_TEST_WEBHOOK_SECRET` from that account's secure webhook
settings. Register the public HTTPS API endpoint above for Webhook V2
`PAYMENT_STATUS_CHANGED`, with signature generation enabled. The webhook secret
is separate from the API token. Receipt does not require a browser session or
Origin. This configuration remains unsupported in production.

All payment results in this continuation were mocked locally; no external invoice
or payment was created. Actual account-originated signed delivery, HTTPS ingress,
completed test-card payment and account-specific replay remain unverified.
The shared public test key does not provide project-owned webhook configuration.
Refunds, disputes, automatic recurring billing and live commercial/provider
decisions remain open as recorded in the original M6 report. This continuation
does not activate live billing or start M7.
