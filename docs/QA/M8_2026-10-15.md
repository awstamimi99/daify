## Reproduction

Use an isolated migrated database whose name contains `test`; the API/browser
suites remove their fixtures. The local test services used here were PostgreSQL
17 on port 55432 (`daify_release_test`, role `daify`) and Redis 7.4.6 on port
56379 (worker tests use database 15). Set `DATABASE_URL` and
`TEST_DATABASE_URL` to that disposable database, `NODE_ENV=test` for API tests,
and `ANALYTICS_TEST_REDIS_URL` to the isolated Redis database.

For quality/build commands, `DATABASE_URL` must exist for Prisma configuration;
use `NODE_ENV=production` for production builds. For adapter packaging:

```bash
NODE_ENV=production \
DAIFY_API_URL=https://api.example.test \
DAIFY_WEB_ORIGIN=https://staging.example.test \
DAIFY_CLIENT_IP_HEADER=x-nf-client-connection-ip \
PROXY_SIGNING_KEY=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA= \
npx --no-install netlify build --offline --context production --filter @daify/web

PROXY_SIGNING_KEY=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA= \
node scripts/check-netlify-artifact.mjs
```

The all-zero key above is a public test canary, never a deployment key.
Local logs are `/tmp/daify-m8-{lint,types,build,api,prototype,browser,netlify,runtime}.log`
and `/tmp/daify-m8-netlify-serve.log`; they are temporary, not durable evidence.

## Remaining gates

Linux CI packaging must pass on the continuation commit. Hosted SSR, QR native
execution, trusted client-IP spoofing tests, real email/storage and idle recovery
require project-owned accounts. Netlify's adapter emits the expected hosted
`/var/task` path, but a successful build does not prove hosted runtime behavior.
Do not work around this by patching generated bundles or weakening auth.

Backups/restore, actual rollback, monitoring, performance, privacy and final
payment acceptance remain open. This is staging preparation, not launch approval.
