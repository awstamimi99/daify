### بيئة قاعدة البيانات

لم يكن Docker أو PostgreSQL مستقل متاحًا محليًا. شغّلت PGlite 17.5 عبر socket محلي على `127.0.0.1:55432`، في الذاكرة، باسم اتصال `daify_qa_test`. نجح اتصال `pg` وتطبيق SQL ملفّي migration بالترتيب. أمر `prisma migrate deploy` فشل برسالة `Schema engine error` في هذه البيئة؛ لذلك **ترحيل الإنتاج غير معتمد بهذه المراجعة**. نجاح اختبارات التكامل هنا يحتاج إعادة تأكيد على PostgreSQL 17 المستقل، خصوصًا التزامن والأقفال والترحيل.

كل الحسابات والبيانات المنشأة تجريبية في هذه القاعدة المؤقتة؛ لم تُستخدم بيانات إنتاج ولم تُرسل رسائل بريد فعلية.

## الأعطال المؤكدة وترتيب الإصلاح

P1: إصلاح قبل استخدام فعلي أو اعتماد الجاهزية. P2: خلل وظيفي/وصولية/بيانات يحتاج معالجة قبل الإطلاق. الأولوية هنا تقييم للمشروع، وليست درجة CVSS.

### D01 — P1 — وسيط تسجيل الدخول يتجاوز فحص Origin

- **إعادة الإنتاج:** POST إلى `/api/v1/auth/login` بمصدر `http://127.0.0.1:8910` يُرفض بـ403. نفس البيانات عبر `/api/auth/login` في Next.js، بصيغة `application/x-www-form-urlencoded` وبنفس المصدر، تُقبل بـ200 وتعيد session cookie.
- **السبب:** الوسيط يستبدل Origin بمصدر موثوق ثابت دون التحقق من مصدر الطلب الوارد. الدليل يثبت قبول الطلب وإصدار الجلسة؛ لم تُنفذ حملة استغلال عبر موقع خارجي.
- **الأثر:** حماية Origin الموجودة في NestJS لا تحمي مسار الدخول الفعلي عبر الويب.
- **الإصلاح والقبول:** التحقق من Origin/CSRF عند حدود Next.js قبل التمرير. اختبار طلبات cross-origin، بما فيها form-urlencoded، ورفضها دون إصدار أو تغيير جلسة.
- **المصدر:** `apps/web/src/app/api/auth/[action]/route.ts:14`؛ الدليل `auth-audit.json → auth-proxy-origin`.

### D02 — P1 — قبول دعوة يتجاوز حماية آخر مالك

- **السبب:** `acceptInvitation` يستخدم upsert لتغيير العضوية، دون تطبيق حماية آخر مالك الموجودة في `updateMember`.
- **الأثر:** مؤسسة تفقد صاحب الصلاحية اللازمة لإدارتها.
- **الإصلاح والقبول:** توحيد قواعد تعديل العضويات وحماية آخر مالك داخل معاملة مناسبة، بما يشمل قبول الدعوات. رفض السيناريو دون تغيير العضوية، ثم اختبار عمليات متزامنة على PostgreSQL مستقل.
- **المصدر:** `apps/api/src/organizations/organizations.service.ts:67`؛ الدليل `auth-audit.json → last-owner-invitation-bypass`.

## ثغرات في التغطية والصيانة تحتاج متابعة

- اختبار Web يستخدم `getByLabel('Password', { exact: true })`، لكن اسم label يتضمن التلميح أيضًا. الفحص أعاد0 لهذا المحدد. بعد إصلاح تأكيد البريد سيحتاج الاختبار أو تركيب TextField إلى تصحيح، وبعده سيصطدم بزر الخروج المخفي. نجاح مراحل سابقة لا يعني نجاح الرحلة كاملة.
- حماية آخر مالك واستهلاك tokens يجريان فحصًا قبل التعديل دون claim ذري واضح في كل المسارات. هذه **مخاطر من قراءة الكود لم تُثبت باختبار تزامن على PostgreSQL مستقل**. يلزم اختبار reset/verification/invitation المتزامن وتعديل المالكين المتزامن.
- الوسيط لا يمرر هوية عنوان العميل، وNestJS يطبّق حدودًا حسب IP؛ يلزم فحص عدة مستخدمين خلف Next.js للتأكد من عدم مشاركة حد الدخول بينهم. ظهر429 أثناء تشغيل عدة جلسات QA، لكنه وحده لا يثبت سلوك مستخدمين من شبكات مختلفة.
- اسم session cookie قابل للضبط في API، بينما proxy في الواجهة وOpenAPI يستخدمان `daify_session` ثابتًا؛ يلزم توحيد عقد الإعداد أو تثبيت الاسم صراحةً. لم يُختبر نشر باسم بديل.
- OpenAPI يسرد المسارات لكن أغلب عمليات الحسابات والمؤسسات لا تصف requestBody أو response schemas؛ يصلح للاستعراض الجزئي ولا يكفي لبناء عميل typed كامل.
- README ما زال يقول إن المصادقة مؤجلة إلىM3 رغم وجودها، وتعليمات التكامل تحتاج توضيح TEST_DATABASE_URL وقاعدة الاختبار. حالة M3 في roadmap ما زالت IN PROGRESS؛ النتيجة الحالية لا تبرر تغييرها إلى COMPLETE.
- لا تتوفر في هذه المراجعة نتائج Firefox/Safari، أجهزة حقيقية، قارئ شاشة، load/stress، مزود دفع وبريد، نسخ احتياطية واستعادة، أو نشر إنتاجي. لم تُختبر كل حالات كل قالب بالعربية. يجب تحديد هذه الجولات قبل اعتماد الإطلاق.
