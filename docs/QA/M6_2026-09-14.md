# M6 sandbox billing — implementation and verification

The owner authorized MyFatoorah public-key testing without creating a merchant
account. Work is on `feat/m6-billing`. This is a sandbox implementation checkpoint;
M6 remains in progress pending full provider/account and commercial acceptance.
No live payment, deployment or production database migration was performed.
Implementation commits: `53c2778` (API/persistence/provider) and `da6a063`
(billing workspace/shared types/browser coverage).

## Implemented

- Immutable KWD plan versions, explicit workspace trial enrollment, subscription
  periods, durable checkout intent, verified payment observations and expiring
  entitlement overrides. Plans can be retired without changing historical prices.
- Limits are checked under the same organization lock as location/menu creation,
  invitation acceptance and member reactivation. Owners consume a seat. Pending
  invitations do not reserve seats; acceptance checks capacity again.
- Design/publish/rollback check allowed template keys and publication access.
  Expiry preserves content editing, existing public menus, media, versions and
  printed QR aliases. Unpublish remains available.
- Owner billing commands require current permissions; trial, checkout and
  cancellation also require AAL2. Platform plan/override commands require admin
  AAL2, a meaningful reason and atomic audit provenance.
- English/Arabic billing UI with test plans, usage, trial/cancellation, hosted
  payment links and status recovery. Public marketing prices remain illustrative.
- Fixed-host MyFatoorah V2 sandbox checkout and authoritative GetPaymentStatus
  checks. A browser redirect cannot grant access. Invoice/reference/amount/KWD
  checks happen before applying provider facts.
- Idempotent checkout/reconciliation. Unknown creation outcomes are retained and
  queried by their unique CustomerReference, never blindly submitted again.
  Pending checkouts prevent another payment intent and subscription cancellation
  until their result is resolved.
- Background reconciliation polls bounded batches of unresolved invoices every
  minute outside tests. Duplicate workers cannot double-apply a payment because
  the database mutation serializes and records unique observations. Unresolved
  rows remain durable after network failures; retry does not create invoices.
- Sandbox mode and test keys are rejected by production configuration. Even if a
  database containing sandbox subscriptions is opened in production, sandbox
  entitlements cannot grant access. Disabling sandbox mode also stops its grants.

## Test policy, not commercial terms

Sandbox fixture version 1 uses Starter 3.000 KWD (1 location, 1 menu, 2 members,
Atelier/Verde/Souk), Pro 5.000 KWD (1 location, 3 menus, 5 members, all templates)
and Business 15.000 KWD (5 locations, 20 menus, 20 members, all templates).
The trial is 14 days; renewal is manual, monthly, with calendar month-end
clamping. A failed paid-plan renewal can receive three days of grace measured
from its original period end; repeated failures do not extend that deadline.
An early same-plan payment extends the paid period by a month. A different paid
plan takes effect when verified, with no test proration/refund; over-limit
content remains stored. Cancellation takes effect at period end. See
[the authorized sandbox policy](../DECISIONS/BILLING.md).

### Actual provider smoke check

Using the public key from [MyFatoorah's API key documentation](https://docs.myfatoorah.com/docs/api-key),
`billing:verify` created sandbox invoice **7173687** for **1.000 KWD**. A second
request through GetPaymentStatus verified the reference, invoice and amount and
returned **Pending**. No card was submitted and no payment was completed.
Successful-payment transitions in local tests use mocked provider responses;
they are not evidence of a completed MyFatoorah payment.

API contract sources:
[ExecutePayment](https://docs.myfatoorah.com/reference/execute-payment),
[GetPaymentStatus](https://docs.myfatoorah.com/reference/get-payment-status).

## Local setup

From the repository root, select an explicitly disposable test database:

```sh
export DATABASE_URL='postgresql://postgres@127.0.0.1:55432/daify_m6_test?schema=public'
export TEST_DATABASE_URL="$DATABASE_URL"
npm run prisma:migrate:deploy --workspace @daify/api
NODE_ENV=test BILLING_MODE=sandbox ALLOW_DEV_SEED=true npm run billing:seed --workspace @daify/api
```

Use your own local PostgreSQL credentials/port if different. The seed is opt-in,
idempotent and audited, and refuses production. It never enrolls a workspace.

The public test key was saved locally in ignored `apps/api/.env.billing` with
owner-only file permissions. Its contents are not committed. For another
checkout, create that file with `BILLING_MODE=sandbox` and
`MYFATOORAH_TEST_API_KEY` copied from the official documentation above.
Keep it server-side. Run the synthetic provider smoke check with:

```sh
set -a
source apps/api/.env.billing
set +a
NODE_ENV=development npm run billing:verify --workspace @daify/api
```

Each deliberate smoke run creates a new unpaid test invoice. For application
checkout retries, use the existing operation/status-check flow instead. An
optional `MYFATOORAH_TEST_RETURN_URL` must be a public HTTPS page; MyFatoorah
rejects localhost callback URLs. Omitting it still permits hosted test checkout
and explicit status checks from the dashboard.

To use the dashboard, launch the normal API/web development processes with the
same local database and API sandbox environment, plus the existing SMTP/MFA/proxy
configuration in `apps/api/.env.example` and `apps/web/.env.example`. Sign in,
enable two-step verification under Account security, then open
`/dashboard/billing`. Trial enrollment explicitly starts enforcing that plan's
limits on the chosen workspace. Prices shown there are test values.

For automated verification:

```sh
npm run build
npm run lint
npm run typecheck
npm run test:prototype
NODE_ENV=test WEB_TEST_PRODUCTION=true npm run test:web -- --workers=2
NODE_ENV=test npm run test:api
```

Browser tests seed the sandbox catalog in their selected test database and start
their own compiled API/web servers. Integration tests clear fixtures, including
billing fixtures, in the explicitly selected test database.
